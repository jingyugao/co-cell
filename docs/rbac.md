# RBAC 与 Sandbox 角色

CoCell 的权限设计围绕 **Sandbox role** 展开：根据任务用途，为环境配置可以访问的资源和可以执行的操作。后续将以角色控制 `glab`、`kubectl` 等工具的权限，让查询、开发与运维任务使用适合各自范围的授权。

## 角色设计

以下角色作为设计示例，具体权限按项目和资源范围配置：

| 角色 | 主要用途 | 权限范围示例 |
| --- | --- | --- |
| 只读分析 | 阅读需求、代码和运行状态 | 读取指定仓库、查看 MR、查询指定 namespace 的资源与日志 |
| 研发 | 实现、测试和提交代码 | 在授权仓库中创建开发分支、推送代码、创建 MR |
| 运维 | 处理环境与发布任务 | 在指定集群、namespace 和资源范围内执行获准操作 |

权限需要同时表达工具、动作、目标资源和执行条件。例如，允许查看某个 namespace 的 Pod，与允许修改其中的 Deployment 是两项不同授权；允许创建 MR，也不自动包含合并或部署权限。

## 授权流程设计

1. 为项目 Sandbox 选择角色与资源范围。
2. 工具执行入口根据角色检查具体动作与目标。
3. 需要人工决定的操作展示目标、执行内容和影响，等待确认。
4. 保存操作结果与来源会话，便于回溯。

角色检查计划放在实际执行入口，并结合服务端凭据权限约束可执行范围。共享 `AGENTS.md` 用于表达工作约定，审批工具用于收集人工决定。

## 当前连接配置

当前单用户实例按操作者统一管理连接配置。连接页支持导入本机 Git、GitLab CLI、MySQL、飞书和 Meegle 等配置，通过 `sandbox.toml` 供项目环境使用。

Kubernetes 通过 `COCELL_KUBECONFIG` 显式指定独立 kubeconfig，再执行 `pnpm credentials:import`。导入过程校验配置，实际集群权限由提供的凭据及集群授权决定。连接配置与业务知识分别保存，长期知识库只记录资源用途和操作约定。

## 人工确认

`request_user_approval` 接收操作标题、目标、执行内容和影响说明，在当前项目与会话中等待使用者决定。工具返回审批结果，实际操作由任务继续执行。
